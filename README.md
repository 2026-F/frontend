# ArtBid Frontend

## 서비스 소개

ArtBid: 신진작가와 초보 컬렉터를 위한 미술품 경매 웹앱

작가나 소규모 갤러리가 작품을 위탁 등록하면 사전 관람(프리뷰)을 거쳐 정해진 시각에 경매가 열린다.
작품 탐색, 라이브 방송, 3D/AR 작품 미리보기와 입찰 화면을 제공한다.
핵심 규칙은 마감 직전 유효 입찰에 따라 기존 마감 시각을 30초 연장하는 안티 스나이핑이다. 입찰 유효성과 최종 마감 시각은 백엔드 응답을 기준으로 표시한다.

[백엔드 저장소](https://github.com/2026-F/Artbid)가 작품, 경매, 인증과 결제 API를 담당한다.

## 문서 활용 기준

- README: 서비스 목적, 구조, 실행 방법과 팀 협업 규칙
- [CLAUDE.md](CLAUDE.md): AI의 작업 절차와 주의사항. Codex는 [AGENTS.md](AGENTS.md)에서 연결
- [작업 기록](docs/prompts/TEMPLATE.md): 개별 작업의 요청, 선택 이유와 검증 결과

‘현재 구현’은 확인 시점의 상태이며 향후 설계를 제한하는 규칙이 아니다.
작업 전 관련 코드와 최신 요구사항을 확인하고, 문서와 차이가 있으면 원인을 파악해 필요한 문서를 갱신한다.
코드가 요구사항과 다를 때는 버그 가능성도 검토하며, 요구사항을 코드에 맞춰 임의로 바꾸지 않는다.

## 현재 구현

문서 기준: 2026-10-26, develop. 화면 구현과 실제 백엔드 연동 검증은 구분한다.

| 영역 | 구현과 확인할 범위 |
| --- | --- |
| 작품 탐색 | 홈, 카테고리, 프로모션, 작품 상세 화면이 있다. API와 목데이터가 혼용된다. |
| 경매 | 목록과 상세, 입찰 패널, 카운트다운, SSE 구독과 폴링 코드가 있다. 실제 입찰 흐름은 백엔드와 함께 검증해야 한다. |
| 라이브 | IVS Real-Time 스테이지 기반 송출과 시청 화면이 있다. 실제 AWS 송출부터 시청까지의 검증은 별도이다. |
| 회원 | 가입, 로그인, 로그아웃, 마이페이지의 로그인 상태 표시가 구현되어 있다. |
| 공간 미리보기 | 카메라 또는 앨범 사진 위 작품 배치와 이미지 저장 흐름이 있다. 공간 인식이나 자동 실측 기능은 아니다. |
| 3D 뷰어 | model-viewer로 작품 모델을 표시하며 사진을 캔버스 모델에 입히는 방식도 있다. AR은 기기와 모델 형식에 따라 별도 확인이 필요하다. |
| 검색과 알림 | 화면 진입점이 있지만 실제 데이터 연동은 완료 상태로 간주하지 않는다. |
| 결제 | 백엔드 Toss API가 있다는 사실만으로 이 저장소의 결제 화면 연동이 완료된 것은 아니다. |

목데이터나 API 실패 시 대체 화면이 보이는 것과 실제 서비스 연동 성공은 다르다.
`frontend/src/lib/lots.ts`, `frontend/src/lib/mock.ts`와 해당 페이지에서 데이터 출처를 확인한다.
문서나 기능 비교 시 대상 브랜치를 확인한다. 이번 조사에서 확인한 브랜치 차이는 [작업 기록](docs/prompts/2026-10-26-ai-collaboration.md)에 남겼다.

### 남은 구현과 연동 계획

- 백엔드는 MSA로 전환할 예정. 서비스 구분은 ① 경매/입찰 + 회원/작품 ② 결제/정산 ③ 라이브 스트리밍이다.
- 레포 구성과 코드 경로는 변경될 수 있다. API 진입점, 인증, 서비스별 호출 방식은 후속 설계에서 확인한다. 현재 단일 API 주소 설정을 영구 계약으로 간주하지 않는다.
- 구조 변경 시 README, CLAUDE.md, AGENTS.md의 참조 경로, CI와 실행 안내를 함께 갱신하고 기존 작업 기록의 연결을 유지한다.
- 공통 인증 오류 처리: [API 응답 인터셉터](frontend/src/lib/api.ts)에 401 리다이렉트 등의 처리 미구현
- 검색, 알림, 결제: 실제 데이터와 API 연동 범위 확인 필요
- 백엔드는 경매와 입찰에 Kafka 도입 예정이며 Redis 사용 여부는 미정이다. 프론트 연동 방식이나 이벤트 계약의 변경 여부는 별도 협의하며, Kafka 도입만으로 브라우저의 직접 연결이 필요하다고 가정하지 않는다.

미구현 항목을 곧바로 확정된 개발 일정으로 해석하지 않는다. 우선순위와 완료 조건은 [관련 이슈](https://github.com/2026-F/frontend/issues) 및 팀 합의로 관리한다.

## 기술 스택

| 구분 | 기술 | 용도 |
| --- | --- | --- |
| 언어 | TypeScript | 화면 로직과 API 타입 정의 |
| 프레임워크 | Next.js 14.2.5 | App Router 기반 페이지와 라우팅 |
| UI 라이브러리 | React 18.3.1 | 화면 컴포넌트 구성 |
| 스타일 | Tailwind CSS | 화면 스타일과 반응형 레이아웃 |

| 상태 관리 | Zustand | 인증 등 클라이언트 상태 관리 |
| 라이브 방송 | Amazon IVS Web Broadcast SDK | IVS Real-Time 스테이지 참여와 방송 |
| 3D/AR | Google model-viewer | 작품 모델 표시와 지원 기기의 AR 진입 |
| 코드 검사와 포맷 | ESLint, Prettier | 코드 규칙 검사와 포맷 정리 |
| 실행 환경 | Node.js 20, npm | CI 기준 런타임과 의존성 관리 |
| CI | GitHub Actions | lint와 build 검증 |

선언된 버전은 [package.json](frontend/package.json), 실제 설치 버전은 [package-lock.json](frontend/package-lock.json)을 기준으로 확인한다.

```text
   └─ public/                   # 이미지와 모델 등 정적 자원
```

## 로컬 실행

명령어는 macOS 터미널과 Windows Git Bash 기준이다.

저장소 루트에서 내부 앱 폴더로 이동한다.

```sh
cd frontend
npm ci
if [ ! -f .env.local ]; then
  cp .env.local.example .env.local
fi
npm run dev
```

기존 `.env.local`이 있으면 덮어쓰지 말고 필요한 변수만 확인한다.

- 기본 접속 주소는 `http://localhost:3000`이다.
- `NEXT_PUBLIC_API_BASE_URL`은 API 서버 주소이다. 로컬 예시는 `http://localhost:8080`이다.
- 이 변수는 브라우저에 공개된다. API 키나 다른 비밀정보를 넣지 않는다.
- 실제 API 검증은 백엔드를 실행하고 허용 출처와 API 응답을 함께 확인한다.
- 현재 `next.config.mjs`에는 API rewrites가 없다. 과거 프록시 설명이나 코드 주석만 믿고 설정하지 않는다.
- 개발 출력은 `.next-dev`, 빌드 출력은 `.next`를 사용한다.

## 검증

내부 `frontend/`에서 실행한다.

```sh
npm run lint
npm run build
```

필요한 경우 별도 타입 검사는 `npx tsc --noEmit`으로 수행한다.
현재 `npm test` 스크립트는 없다. `npm run format`은 파일을 변경하므로 검사 전용 명령으로 사용하지 않는다.

- UI 변경은 해당 화면, 주요 상호작용, 오류 상태를 확인한다.
- 카메라는 HTTPS 또는 localhost에서 검증한다. 권한 거부 시 앨범 사진 선택 흐름도 확인한다.
- 합성 이미지 저장은 이미지 서버의 CORS 영향을 받는다.
- 모바일 제스처, 이미지 공유, AR은 실제 기기 검증 여부를 따로 보고한다.
- AWS 방송과 실제 API 연동을 확인하지 못했다면 이유와 후속 확인 방법을 적는다.

CI는 Node.js 20에서 `npm ci`, lint, build를 실행한다.
현재 경로 필터 때문에 루트 문서만 수정한 PR은 프론트 CI가 실행되지 않을 수 있다.
문서 변경의 검증은 링크, 명령과 실행 위치, 현재 코드와의 일치를 기준으로 한다.

## 협업 규칙

### 브랜치

- `main`: 배포 가능한 상태만 유지. 직접 커밋 금지. PR로만 병합.
- `develop`: 트랙별 기능을 모으는 통합 브랜치. 여기서 `feature/{기능}/{작업}` 또는 `fix/{작업}` 브랜치를 만든다. 문서 작업은 `docs/{작업}`을 사용한다.
- 작업 브랜치에서 `develop`으로 PR을 보내고, 통합 확인 후 `main`에 반영한다.
- `main`과 `develop`에 force push하지 않는다.
- 셀프 merge는 하지 않는다(팀장이 확인 후 머지).

### 커밋 컨벤션

Conventional Commits 형식을 사용한다.
`type: 내용` (한글 가능)
PR 제목 작성 시에도 참고한다.

- feat: 새 기능 추가
- fix: 버그 수정
- refactor: 동작 변화 없는 코드 개선
- test: 테스트 코드 추가/수정
- docs: 문서(README, 주석) 변경
- chore: 빌드 설정, 의존성 등 잡일
- style: 포맷팅 등 코드 스타일 변경(로직 변화 없음)

### 변경 공유

- AI가 외부 문서에 접근할 수 없으면 확인하지 못한 범위를 알리고, 작업에 필요한 내용은 팀원에게 확인한다.
- 화면을 변경한 PR에는 변경 결과를 보여주는 스크린샷을 첨부한다. 개인정보와 토큰이 포함되지 않도록 확인한다.
- API나 엔티티 필드 등 인터페이스가 바뀌면 관련 명세와 ERD도 갱신한다.
- 상대 저장소 변경이 필요하면 해당 이슈나 PR을 연결하고 선행 작업 및 연동 검증 여부를 적는다. 번호가 정해지지 않았으면 미생성으로 명시하고 생성 후 연결한다.
- PR 병합과 기능 검증 완료를 구분한다. 이슈 완료 조건에 남은 작업이 있으면 후속 작업을 명시한다.

## AI 협업 기록

팀 공통 지침인 [CLAUDE.md](CLAUDE.md)에 따라 작업한다. Codex는 [AGENTS.md](AGENTS.md)를 통해 같은 지침을 읽는다.

설계 대안 선택, API 계약 변경, 원인 분석이 필요한 오류 해결, 보안 또는 외부 연동 방식 변경은 [기록 양식](docs/prompts/TEMPLATE.md)을 사용해 `docs/prompts/YYYY-MM-DD-주제.md`에 남긴다.
단순 오탈자나 색상 변경은 별도 기록 없이 PR의 히스토리 항목에 '해당 없음'과 이유를 적는다.

1. 중요한 결정이 생기면 AI가 기록 시작 날짜와 구체적인 주제로 파일을 만든다. 파일명은 `YYYY-MM-DD-주제.md` 형식으로 작성한다.
2. 같은 작업에서 진행 중인 후속 요청과 결정은 기존 파일에 추가한다. 날짜가 바뀌면 날짜를 구분하고, 이전 판단은 덮어쓰지 않는다. PR 생성 후에는 해당 PR을 기준으로 기록 범위를 구분한다.
3. 작업 완료 시 AI가 실제 검증 결과와 미확인 사항을 정리한다.
4. 담당자가 핵심 요청, 선택 이유, 수정 내용, 검증 결과를 확인한다.
5. PR의 **프롬프트 히스토리** 항목에 생성하거나 갱신한 기록 파일을 연결한다.
6. PR 병합 후 이어지는 작업은 새 파일에 기록하고 이전 기록과 PR을 연결한다.


- 기록은 대화 전체를 복사하는 대신 핵심 요청, AI 제안, 채택하거나 제외한 이유, 직접 수정하거나 재요청한 내용, 검증 결과를 담는다.
- 병합된 기록은 보존하되, 오탈자와 사실 오류는 정정 이유를 남기고 수정할 수 있다. 민감정보는 발견 즉시 제거하며 원문을 정정 이력에 남기지 않는다.
- 확인되지 않은 사람의 판단이나 과거 프롬프트는 만들어 쓰지 않는다. 비밀정보와 개인정보는 원문에서 제거한다.

두 저장소에 걸친 결정은 주된 결정을 내린 저장소에 상세 기록을 두고 상대 PR에서 연결한다.
PR에는 실제로 실행한 검사와 미검증 사항을 구분하고, 보안 관련 변경이면 타인 접근 거절 등 필요한 실패 사례도 확인한다.
