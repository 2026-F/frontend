# 경매 상세와 목록의 상태 동기화

- 작성일: 2026-11-09
- 관련 이슈 / PR: [FE #53](https://github.com/2026-F/frontend/issues/53), [FE #59](https://github.com/2026-F/frontend/pull/59), [FE #61](https://github.com/2026-F/frontend/pull/61), [FE #63](https://github.com/2026-F/frontend/pull/63), [BE #96](https://github.com/2026-F/Artbid/issues/96), [BE #107](https://github.com/2026-F/Artbid/pull/107)

## 목적

상세를 열어 둔 동안 입찰 가격과 이력이 뒤로 돌아가거나 누락되는 문제를 보완한다. 구매자 목록은 최신 경매를 연결하고 관리자는 상태 변경 결과를 서버 기준으로 확인한다.

## 핵심 요청

요약: 팀장 PR의 로그인 입찰, 입찰 이력, 개별·일괄 재오픈을 유지하며 FE #53의 상세 복구, 서버 기준 타이머, 목록 갱신, 관리자 재조회를 구현한다. 프론트 PR을 먼저 준비하고 Kafka 없이 BE #96과 통합 검증한 뒤 이슈를 닫는다.

## 선택과 이유

| 검토한 방법 | 선택 | 이유 |
| --- | --- | --- |
| 기존 `/live`와 SSE로 상태 수렴 | 채택 | 가격, 상태, 마감과 버전이 함께 온다. 버전 0은 직접 조회와 일치할 때 기준으로 삼는다. |
| 입찰 POST 응답으로 화면 상태 교체 | 제외 | 버전이 없어 먼저 받은 새 SSE 상태를 덮을 수 있다. 성공하면 상태와 이력을 다시 읽는다. |
| 서버 시각 간 차이와 브라우저 경과 시간 사용 | 채택 | 시간대 없는 서버 시각을 브라우저의 지역 시각과 직접 비교할 때 생기는 오차를 제거한다. |
| 현재 페이지 단위 조회, 목록에 서버 시각 표본 한 개 | 채택 | 기존 페이지와 카드 필터를 유지하며 새 경매 ID를 반영한다. 카드마다 연결하는 방식은 제외한다. |
| 관리자 수동 변경 성공·거절 뒤 행 재조회 | 채택 | 화면에 요청값을 대신 쓰면 서버가 반영한 작품 상태나 동시에 바뀐 경매를 놓칠 수 있다. |

## 반영 내용

- 상세 진입·재연결·탭 복귀 때 상태와 이력을 읽는다. 연결이 끊긴 동안 보이는 탭에서 5초 간격으로 보정하고 경매 ID가 바뀌면 이전 요청을 취소한다.
- 마감 시각이 지나면 입찰 입력과 제출을 막고 마감 확인 중으로 표시한다. 최종 상태는 서버에서 받는다.
- 구매자 목록은 보이는 탭에서 30초 간격과 탭 복귀 시 현재 페이지를 다시 읽는다. 조회 실패 시 마지막 정상 목록을 유지하고, 개별 경매 조회 실패 시 연결 ID가 같을 때만 이전 경매 상태를 보존한다.
- 관리자 행은 서버의 작품 상세와 연결 경매를 반영한다. 변경 오류와 재조회 실패를 구분하고 재시도를 제공한다.

## Docker 실제 백엔드 추가 검증

Docker Desktop 복구 후 FE PR #67 (`4724289`)과 BE develop (`d12a543`)을 격리된 PostgreSQL 16·Redis 7에 연결했다. Kafka를 끄고 백엔드는 UTC, 브라우저는 Asia/Seoul로 설정했다.

- 두 실제 계정으로 로그인했다. A의 입찰이 B 화면에 SSE로 반영됐고, B의 마감 직전 입찰로 경매가 연장됐다. 연결 차단 후 새로고침으로 입찰 이력이 중복 없이 복구됐고, 열어 둔 목록도 새 가격을 표시했다.
- 자동 마감이 두 상세 화면에 반영됐다. PostgreSQL에서 낙찰 정산 1건을 확인했다. 관리자 재오픈 API 호출 후 열린 목록에 새 경매 링크가 표시됐고, 비로그인 입찰은 401로 거절됐다.
- BE #96 재현: 관리자 수동 시작 후 DB 기반 조회는 `ONGOING`이었지만 실시간 조회는 `PREVIEW`였다. 마감 전 수동 `CLOSED` 요청도 204로 수락됐다.

미검증: 실제 백엔드에서 새로고침 없는 재연결, 수동 마감과 스케줄러 경합 시 정산 1회 생성, 배포 환경. [#53 검증 결과](https://github.com/2026-F/frontend/issues/53#issuecomment-6755663849)

## 남은 작업

- BE #96 반영 후 수동 변경의 DB·실시간 조회·SSE 일치 여부를 확인한다. 수동 마감이 정상 마감·정산 경로를 우회하지 않는지와 스케줄러 경합 시 정산이 한 번만 생성되는지 확인한다.
- Kafka 비활성 상태에서도 정산과 SSE는 기존 경로에서 처리된다. 낙찰 마감 때 새 outbox 대기 행이 생성되는 부분은 Kafka 제거 작업에 전달할 항목이다.
- 프론트 리뷰·병합과 실제 백엔드 통합 검증을 모두 마친 뒤 FE #53의 완료 여부를 갱신한다.
