# 관리자 작품 목록 페이지 누락과 경매 조회 실패 처리

- 작성일 2026-11-12
- 관련 이슈 [frontend #68](https://github.com/2026-F/frontend/issues/68)

## 목적

관리자가 상태별 전체 작품을 확인하고, 연결 경매 조회에 실패하면 해당 작품에서 다시 조회할 수 있게 한다.

## 핵심 요청

- #68을 먼저 진행한다. 기존 API로 상태별 전체 페이지를 조회하고, 경매 미연결과 조회 실패를 구분해 행 단위 재시도를 제공한다.
- PR #67의 관리자 재조회 흐름을 사용하고, 개별·일괄 재오픈을 검증한다. 목 API 검증과 실제 연동 여부를 기록한다.
- 원격 `develop` 기준으로 작업한다. 커밋 100줄·PR 600줄 내외를 목표로 diff, 커밋 메시지, PR 본문과 화면 캡처를 로컬에서 검토한다.

## 선택과 이유

| 검토한 방법 | 선택 | 이유 |
| --- | --- | --- |
| 관리자 페이지 이동 | 제외 | 일괄 재오픈에서 ‘전체 선택’이 가리키는 범위도 함께 바뀐다. |
| 상태별 전체 페이지 조회 | 채택 | 기존 정렬과 일괄 선택 범위를 유지하면서 후속 페이지를 읽는다. |
| 경매 조회 실패를 행 단위로 표시 | 채택 | 다른 작품을 계속 관리할 수 있고, 실패한 행은 최신 작품과 연결 경매를 다시 조회할 수 있다. |

## 반영 내용

- 원격 `develop`의 `72ed401`에서 `fix/68-admin-artwork-pagination`을 시작했다.
- 기존 페이지 API로 상태별 마지막 페이지까지 읽고 작품 ID로 중복을 제거한다. 연결 경매 조회는 여섯 건씩 실행한다.
- 경매 조회 상태를 미연결·조회 완료·실패로 구분한다. 실패한 행은 조회를 다시 시도할 수 있고 경매 생성·변경·재오픈은 조회 상태에 따라 표시한다.
- PR #67의 관리자 상태 변경 후 재조회에 동일한 경매 조회 판정을 적용한다.

### 실제 백엔드 연동 검증

2026-11-13에 Artbid `develop`의 `666a7a6`과 격리된 로컬 PostgreSQL 16·Redis 7을 사용했다.

- 실제 API로 프리뷰 작품 101개를 만들었다. 두 번째 페이지 응답에 101번째 작품이 포함됐고 관리자 화면에도 표시됐다.
- 브라우저에서 연결 경매 조회 요청 한 건을 끊어 오류 표시를 확인했다. 행의 다시 조회를 누르자 실제 API가 200을 반환하고 경매 정보가 복구됐다.
- 관리자 상태 변경은 204, 직접 마감 요청은 409를 반환했다. 재조회와 실제 API에서 진행 중 상태를 확인했다. 판매자 계정은 관리자 화면 진입이 제한됐다.
- 일괄 재오픈은 목 API로 검증했다.
