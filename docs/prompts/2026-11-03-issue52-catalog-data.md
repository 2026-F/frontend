# FE #52 작품·경매 실데이터 연결

- 작성일: 2026-11-03
- 관련 이슈: [FE #52](https://github.com/2026-F/frontend/issues/52), [BE #99](https://github.com/2026-F/Artbid/issues/99)

## 목적

작품과 경매를 실제 API 관계로 조회하고 화면마다 같은 정보와 이동 경로를 보여준다.

## 핵심 요청

요약: 원래 이슈 [FE #52](https://github.com/2026-F/frontend/issues/52)와 해당 PR의 작업 범위를 대조해 정리했다. 사용자 프롬프트 원문 인용이 아니다.

- 홈·경매 목록·카테고리를 실제 작품·경매 API에 연결하고, 조회 실패를 목데이터나 가상 경매로 대체하지 않는다. 카테고리를 임의로 치환하지 않는다.
- 경매 상세는 URL의 경매 ID로 조회한 뒤 응답의 작품 ID로 작품을 연결한다. 작품 상세 직접 진입과 경매를 거친 진입에서 연결 경매·가격·입찰 가능 여부가 같아야 한다.
- 경매가 없는 작품은 작품 상세로 이동하고 입찰 기능을 표시하지 않는다. 목록 첫 페이지를 검색하거나 쿼리스트링을 신뢰해 연결 경매를 추측하지 않는다.
- 빈 목록, 없는 작품·경매, 권한 없음과 API 장애를 구분하고 재시도를 안내한다. 경매 조회 실패를 경매 없음으로 숨기지 않는다.
- API 페이지 정보를 유지해 페이지 크기가 작아도 모든 작품에 접근할 수 있게 한다. 화면마다 가격·상태·대표 이미지 선택을 맞추고, CLOSED만으로 낙찰가라고 단정하지 않는다.
- 기존 API를 사용하며 새로운 catalog API나 전역 정규화 저장소는 만들지 않는다. 필요한 최소 관계 필드는 백엔드와 맞추고 입찰 인증·실시간 구독 개선은 #53으로 남긴다.

### 작업 분리 배경

FE #52를 세 PR로 나누고 기록을 각각 작성하라는 후속 요청에 따라, 이 PR은 #55의 공통 준비 작업에 이어 작품·경매 조회와 화면 간 정보 일치를 담당한다. 미디어 대체 제거는 #57로 분리했다.

## 선택과 이유

| 방법 | 선택 | 이유 |
| --- | --- | --- |
| 경매 조회 후 응답의 작품 ID 사용 | 채택 | 서로 다른 ID를 혼동하지 않는다. |
| 작품 상세의 서버 `auctionId` 사용 | 채택 | 쿼리스트링이나 목록 첫 페이지로 관계를 추측하지 않는다. |
| 페이지 정보 유지 | 채택 | 목록과 카테고리에서 다음 작품에 접근할 수 있다. |

## 반영 내용

목록·상세 조회와 카드의 가격, 상태, 이미지 및 링크를 정리한다. 현재 페이지에만 적용되는 경매 상태 필터를 명시한다. 실패한 경매 조회를 경매 없음으로 표시하지 않는다. 기존 입찰 컴포넌트는 타입과 표시 호환만 수정하며 로그인 입찰·이력·SSE 개선은 #53에 남긴다.

## 검증

| 확인 항목 | 방법 | 결과 |
| --- | --- | --- |
| 빌드 | `frontend/`에서 `next build` | 성공. 이미지·폰트 lint 경고가 남았다. |
| ID 연결 | 실제 로컬 API와 브라우저 | 서로 다른 작품·경매 ID와 잘못된 쿼리스트링 확인 |
| 페이지와 정보 일치 | 실제 로컬 API에서 size=2로 순회 | 모든 작품 접근과 목록·상세의 이미지·경매 ID 일치 확인 |
| 오류 처리 | 별도 로컬 서버에서 응답 주입 | 빈 목록, 403, 404, 500, 통신 장애 및 재시도 확인 |

위 실제 API와 응답 주입 검증은 분리 전 동일한 최종 구현에서 수행했다. 빈 실제 DB와 배포 환경은 확인하지 않았다.
